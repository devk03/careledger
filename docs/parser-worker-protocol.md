# Structural-parser boundary (protocol only)

This is the protocol for a dedicated parser helper in the private TypeScript pilot. `server/src/ingest/parserProtocol.ts` defines the request/reply contract, `server/src/ingest/parserSocket.ts` implements its bounded Unix-socket client, and `server/src/ingest/parserWorker.ts` now provides a development worker. It independently hashes exact request bytes and decodes JPEG/PNG, but rejects PDFs. **No OS-isolated parser deployment or upload route exists yet.** A worker passing synthetic tests is not permission to ingest medical files.

The TypeScript server remains the only database writer. After admission and malware scanning, it will send one bounded file per request to a trusted local Unix socket. The request is a four-byte big-endian JSON-header length (at most 512 bytes), that exact UTF-8 JSON header, and exactly `byteSize` binary file bytes (at most 30 MiB). The client then half-closes its write side; the worker must wait for end-of-input and reject any excess or missing bytes before replying. The worker will reply with a four-byte big-endian JSON length and at most 2,048 bytes of strict UTF-8 JSON, then close the connection. Both sides must reject incomplete, excess, or mismatched framing. The binary payload is the full document and can contain identifying text; the JSON metadata must not contain filenames, document text, arbitrary parser errors, or user-provided shell arguments.

The header binds a random request ID, media type, SHA-256, byte size, protocol version, and policy version. A reply must echo those fields exactly and carry the expected pinned worker version. **Echoing the digest is not proof of inspection:** the worker must read exactly `byteSize` binary bytes, independently hash them, compare the result to the header digest, and only then return `safe`; the server must send bytes verified against the staged original. A safe PDF reply must report page/object counts and maximum page dimensions within pilot limits and explicitly assert no encryption or active content. A safe JPEG/PNG reply must report one frame, one page, and bounded pixel dimensions. A rejection carries only a fixed code. Timeouts, crashes, malformed or oversized replies, unsupported fields, version drift, and unavailable workers fail closed.

The helper must decode and inspect the *entire* file with mature format libraries; PNG preflight and PDF byte-marker searches are insufficient. It must run as a non-root, network-disabled, read-only, resource-limited service with a narrowly scoped local socket; the application must not have control of a Docker daemon or general container-launch socket. Limit CPU, memory, process count, concurrent requests, and wall time. The helper should have no database or object-store access. Transport authentication, isolation, and the absence of sensitive text in worker-supplied metadata are trusted-worker/deployment properties, not guarantees made by the JSON schema. Raw replies must not be logged.

The adapter rejects early, mismatched, truncated, excess, timed-out, and unavailable replies. The development worker waits for request EOF, independently hashes exact payload bytes, rejects excess or missing bytes, and uses `imageDecoder.ts` to force JPEG/PNG pixel decoding with a pinned Sharp/libvips dependency. A decode that exceeds its wall-clock deadline terminates the dedicated worker process; after request half-close, client disappearance may be unobservable until a write, so the deadline is the fallback. It is not isolated and is not called by Express. PDF inspection, a constrained worker image/runtime with memory/CPU limits and restart policy, and synthetic tests for malformed/active/encrypted PDFs, excessive pages/objects/geometry, animation, decompression bombs, and staged-byte replacement remain. Do not wire this into `inspectStagedOriginal` or a user-facing upload route until those tests and the sandboxed deployment pass review.
