# Parser sandbox smoke record

Synthetic-only local check on Docker Desktop Linux/arm64, 2026-09-24. No family records or application database were mounted. This is a record of a completed test, **not a copy-paste runbook**. Its image tag, Compose project, and container names were already used. A future test must use a unique image tag, project, and container names, and must verify the exact Compose project label, image ID, and container ID before signaling any container. Never target an app or family-record container. Stopping the test worker left its containers and socket volumes in place.

Observed: worker UID/GID `10002:10003`; socket directory `10002:10003`, mode `0710`; live `parser.sock` `10002:10003`, mode `0660`; executable JS root-owned and not writable by the worker; Sharp/libvips loaded. The worker had no Docker network, ports, database mount, or record volume. Idle PID use was 12 under the revised 64-PID cap. A separate UID `10001` client in group `10003`, with the named socket volume mounted read-only and no network, submitted a generated 2×3 PNG and received `{"status":"safe","pageCount":1}`. This proves that socket access worked in this synthetic environment, not that arbitrary uploads are safe.

Observed: the competing `flock` process exited `1` without moving the live socket. After the forced crash, the same worker container restarted and stayed running; its private volume contained `worker.lock`, a new `parser.sock`, and one archived `stale-*.sock`. No socket was deleted by the recovery code. The preview was stopped afterward, leaving the test containers and volumes recoverable.

On 2026-09-25, a fresh synthetic-only Compose project tested `restart: on-failure:3`. The exact container's Compose project/service labels, image ID, sole socket-volume mount, and policy were verified before fault injection. After the Node worker process received `SIGKILL` inside that container, Docker reported `RestartCount=1`; the worker was running, the old socket had been archived, and a generated 2×3 PNG returned `{"status":"safe","pageCount":1}` through the new socket. The container was then stopped, not deleted, and its test volume was left intact. This demonstrates one crash recovery on Docker Desktop Linux/arm64; it does not prove recovery from an unhealthy-but-running process, host/daemon restart, or exhaustion of the retry budget.

Also on 2026-09-25, an initial generated-image healthcheck passed in a synthetic-only Compose project, but adversarial review found that its timeout could disconnect a slow decoder and kill the worker. That design was not published as a usable healthcheck. The replacement uses a separate worker-owned `health.sock` control socket; its probe does not enter the document decoder or consume document-request capacity. Synthetic unit coverage checks an absent socket, a response while document decoding is busy, and stale health-socket recovery. In a fresh synthetic-only Compose project, the verified replacement image reported `healthy`, with `health.sock` mode `0600` and `parser.sock` mode `0660`. After the exact Node worker process was killed inside that verified container, Docker reported one restart, both stale socket inodes were archived, both sockets rebound at their expected modes, and the control probe again succeeded. The container was stopped, not deleted, with its test volume retained. This is a liveness signal, not a security attestation; Docker's `on-failure` policy does not restart a running container merely because its health status turns unhealthy.

Still required before medical uploads: test the target Linux host architecture and cgroup enforcement, operator alerting and recovery from unhealthy status or exhausted retries, concurrent/large-image load, PDF inspection, ClamAV provisioning, authenticated upload and source grants, object/DB recovery, and an approved migration/cutover. Keep the parser disconnected from Express until these pass.
