# Managed browser upload journal — unmounted candidate

The browser-only `draftUploadJournal` saves one exact-tuple record for a draft reservation in same-origin `localStorage`: opaque household/account/session/reservation and intent/blob IDs, the SHA-256 and length of each encrypted v2 wire, and a per-role `prepared` or `attempted` flag. It saves and reads the digests back before either upload. With a Web Lock on that tuple, it saves `attempted` **before** the first POST. Every outcome, including HTTP 201, 409, timeout and network failure, is followed by the read-only exact-byte receipt. While that journal record survives, a second tab or later call cannot POST that role again. A reload can reconcile both receipts without sending ciphertext. A mismatched wire or receipt fails closed.

A fictional Chromium test exercises reload, two tabs competing for one role, a tampered wire, cross-family exact-tuple lookup, a lost upload response with a committed receipt, a 409 with an unconfirmed receipt, and no second POST. It checks that the local journal contains neither the invented note text nor its care date. This is browser storage/network-mock evidence, **not** a mounted server flow or power-loss durability test.

The journal intentionally stores no ciphertext wires or device keys. Therefore a reload may establish that an upload committed but cannot sign/publish the pair without the original wires and keys. Browser storage may be evicted or lost; if the caller re-creates a missing record with retained wires and IDs, this small journal alone cannot prove a prior POST did not happen. An unavailable Web Lock or storage operation denies upload. It does not reclaim a charged server lease, make an unconfirmed receipt safe to retry, replace an authenticated backup, or satisfy the separately permission-gated device-key store. Do not mount the managed upload flow for family records on this basis alone.
