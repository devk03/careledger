# Managed lease lifecycle proposal — design only

No migration SQL has been created or applied for this proposal. The existing managed v10 schema remains authoritative only for fictional testing. This proposal needs explicit permission before a migration is drafted, and a separate permission before it is applied even to a disposable fictional database. It must never auto-apply to the community, Hermes, Railway or real-family databases.

## Why v10 cannot open public intake

`managed_wire_occupancy` counts uncommitted day and non-day staging leases forever. Their rows are immutable except when a successful blob commit marks them committed. If an upload is interrupted or its intent expires, it cannot finish, but its lease still charges family and global quota. Repeated abandoned uploads can exhaust capacity. Draft reservations and four ID claims per reservation also remain permanently stored. The eight-per-device/ten-minute and 128-per-family/day issuance bounds slow bursts; they do not reclaim logical quota or metadata storage.

## Proposed forward-only change

Retain every existing intent, lease, reservation, ID/nonce/object claim and committed blob. Add an append-only reconciliation-run record with a unique run ID, operator/service identity, observed database snapshot and object-inventory digests, time and outcome. Add separate immutable terminal release records with composite household keys for day leases, source-only non-day leases, and a **single draft-pair release record** that binds one household/reservation plus both exact role-specific intent IDs and attempt IDs. No individual terminal event may apply to either draft role. The effective view excludes both draft leases only when that one pair event is valid; a one-sided release is impossible.

Create a new effective-occupancy view rather than silently changing v10's view. It counts committed blob wire bytes plus **uncommitted** leases (`committed_at IS NULL`) without a valid terminal release record. Counting committed leases as well would double-charge their blobs. A valid release must match lease kind, household, intent, attempt and—for drafts—reservation and both roles; it must bind expiry/unconsumed evidence, absence of a committed blob, the immutable reconciliation-run digest and the active schema version. Invalid, mismatched or duplicate events leave the lease charged and raise an auditable error. All managed writers must switch to that view in one reviewed binary/schema cutover; old writers must fail closed on the new schema version. A terminal event is never an ID or nonce release: collision claims remain immutable. The event stream and view need database-enforced linkage, one terminal decision per lease or pair, immutable rows and idempotent replay.

An expired intent alone is **not** release evidence. A global managed-writer barrier must stop intent/lease opening, object writes, blob commits, day/non-day publication and reconciliation outside this run; drain every in-flight operation, then hold the fence through inventory and release commit. Any out-of-band writer invalidates the result. The fenced writer takes a consistent SQLite/object snapshot and classifies every possibly staged object. Inside the release transaction it rechecks lease identity, expiry, unconsumed state and no committed blob or pending pair. A lease can be released only if exact attempt IDs match and every staged object is verified as retained or quarantined. Missing, corrupt, unknown or incompletely inventoried objects keep it charged. For draft pairs, both intents and both leases must qualify in the same transaction. A crash before the release transaction leaves quota charged; after commit, the event remains durable and replayable. No cleanup operation may delete or overwrite source objects or records as a side effect of this migration.

Logical wire quota and physical disk capacity are separate. Retained orphan ciphertext remains physically charged even if an expired logical lease is released. Existing inventory reports file lengths per inode, not allocated filesystem blocks; it cannot alone enforce a production disk cap. The future admission gate must check authoritative available allocated blocks on **each** database, object and backup volume, accounting for committed, pending, orphan, hard-linked, SQLite/WAL/SHM and backup usage as the volume actually reports it. Under the same writer policy, it must reserve worst-case incoming wire, SQLite/WAL expansion and configured safety headroom before a write. Missing, stale or insufficient volume evidence blocks admission; logical release never overrides that block. The exact headroom must be measured on the target host and tested under disk-full injection before public intake. Authenticated backups must include lifecycle events and reconciliation evidence in their pinned DB snapshot. A separately built independent latest signed-head witness remains a release precondition; this migration does not supply it. Restored services must verify the pinned backup, objects and witness, then reconcile before accepting new writes.

## Required fictional acceptance

- Two unrelated fictional families; releasing one family's expired lease changes neither the other's rows nor its quota.
- Day and source leases: exact lease/attempt match, expiry, no committed blob, and storage-verified classification required; duplicate release is idempotent.
- A draft pair: both expired/uncommitted leases release atomically or neither does; a one-sided attempt fails.
- Inject interruption before and after inventory, event transaction and backup snapshot; never undercount logical or physical bytes.
- Unknown, corrupt, missing and incompletely inventoried objects prevent logical release. A verified retained orphan may permit logical release only while its physical bytes remain charged and the conservative physical capacity gate passes. No automatic physical deletion.
- Two independent writers contend at a one-pair global quota; exactly one pair is admitted and no half-pair persists.
- Fresh restore of two fictional families preserves committed ciphertext, release history and quota accounting; no real records or production DB involved.
- Signed schema checks, foreign keys, private-file modes, full TypeScript suites, privacy audit and independent adversarial review pass before a route is mounted.

This proposal does not solve permanent reservation/claim metadata growth, safe PDF inspection, client key persistence, signup, recovery, MCP consent or real-record readiness. Those remain separate gates.
