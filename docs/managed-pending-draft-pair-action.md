# Pending draft-pair signed action — unmounted contract

This is a device-authored proposal to place **two already committed ciphertext blobs** into the pending adult-review inbox. It does not approve or publish a care day, interpret medical content, or let the hosted server decrypt anything. An unmounted v10 SQLite writer and unmounted same-origin HTTP route exist for isolated fictional testing; neither is mounted in the deployed app, and no database migration was created or applied for this slice.

The shared `encodePendingDraftPairActionPayloadV1` encodes exactly 480 bytes, never JSON: `ADPP` magic; format, Ed25519/SHA-256 suite, a dedicated *register pending pair* operation byte and predecessor flag; 13 ordered opaque 16-byte IDs (household, profile, draft scope, key, reservation, content/metadata intents, content/metadata blobs, content/metadata AAD objects, author device, session); draft key epoch and purpose; author counter and pair time; content/metadata v2 wire lengths; and seven 32-byte digests (key commitment, current active-key head, current contribution-grant head, both exact ciphertext wires, predecessor action, enrolled author signing key). All integers are big-endian. Filenames, note text and care dates stay encrypted in metadata and are absent from the signed payload.

Before signing, the browser opens a draft-purpose HPKE key envelope for the claimed author device and verifies that its scope identity, key ID, epoch and key-material commitment match the signed claims. It then opens both copied v2 wires with that nonextractable envelope-unwrapped key and their claimed AAD object IDs. The authenticated metadata must name the exact content blob and match its plaintext digest, size and file/note format. The signer clears returned file bytes immediately after checking. It queries both same-origin upload receipts by their signed intent/blob IDs and requires `committed` responses matching each copied wire's exact SHA-256 and byte length; `unconfirmed`, mismatched or unavailable results block signing. The pair time is taken after those checks, then the browser signs the 480 bytes with its non-exportable Ed25519 private key. The pending-pair digest is `SHA-256(payload)`. The chained action digest is `SHA-256("adeno:managed:pending-draft-pair-action-hash:v1\0" || payload || signature)`. The existing v10 SQL action kind remains `review` because its trigger requires that value; the signed operation byte and domain distinguish *submitting a pending pair* from any future adult approval. The signer does not establish that the envelope issuer is authorized or the grant remains current; those are separate signed-envelope and transaction checks.

The pure server verifier checks the exact payload, signature, action digest, counter/predecessor, session/device, paired time and current key/grant evidence against caller-supplied authoritative state. It does **not** establish that the state was actually loaded from SQLite or prove either blob was uploaded. Receipt results are point-in-time evidence, not an atomic grant/commit proof. The unmounted writer loads the reservation, both role-specific intents and committed blobs, wire hashes and lengths, enrolled key, current key/grant heads, account/session/device binding and prior action **inside one `BEGIN IMMEDIATE` transaction**. It rechecks CSRF and active authority, verifies the signature, then inserts the signed action and pending pair atomically. The device must separately decrypt/authenticate both wires again before review UI exposure. A missing receipt is never proof an intent may be retried.

Browser tests sign genuinely encrypted fictional drafts with mocked committed receipts and reject a wrong key, changed AAD object, tampered content, validly encrypted but unrelated metadata, unconfirmed receipts and mismatched wire hashes or lengths. An isolated fictional HTTP path now commits and receipts non-day draft ciphertext; a separate unmounted route accepts a canonical signed pair and derives its digests server-side. The private-copy test checks cross-family, CSRF, Origin, claim-tamper, signature-tamper, limiter denial, atomic insertion and exact immediate replay. A second SQLite writer lock produces a retryable 503; the same signed request succeeds after release. It does **not** run the browser signer through the HTTP route, test delayed replay, or establish real enrollment/grant proofs for its structural fixture. No public route is mounted and crash-safe local persistence of the pre-upload wire digest is missing. The server verifier and SQL currently allow only five seconds of clock skew, which can reject a valid pair on a slow network or a mis-set device clock; this needs an explicit freshness policy before mounting. A separate structural one-byte wire vector tests the shared payload/Ed25519 contract across browser and Node; those structural bytes are **not** an authenticated draft and the browser signer rejects them. The browser signer's 16 MiB content cap is narrower than the v10 SQL draft-intent allowance; the writer and browser must adopt one consistent bound. This is not evidence of a mounted write path or an independently auditable persisted record. V10 stores the payload digest and signature but **not the exact canonical payload**. After heads change, an independent auditor cannot reliably reconstruct that preimage. Durable immutable payload retention, anchored to the action and included in authenticated backups, needs a separately reviewed design and any necessary migration approval. The unmounted writer conservatively requires the reservation still to be within its ten-minute window for a new submission, even after both blobs committed in time; exact replay of an existing immutable pair does not require the reservation or mutable heads to remain current. SQL alone does not enforce new-submission expiry.
