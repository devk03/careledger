# Pending draft-pair signed action — unmounted contract

This is a device-authored proposal to place **two already committed ciphertext blobs** into the pending adult-review inbox. It does not approve or publish a care day, interpret medical content, or let the hosted server decrypt anything. No route or writer currently mounts this action; no database migration was created or applied for it.

The shared `encodePendingDraftPairActionPayloadV1` encodes exactly 480 bytes, never JSON: `ADPP` magic; format, Ed25519/SHA-256 suite, a dedicated *register pending pair* operation byte and predecessor flag; 13 ordered opaque 16-byte IDs (household, profile, draft scope, key, reservation, content/metadata intents, content/metadata blobs, content/metadata AAD objects, author device, session); draft key epoch and purpose; author counter and pair time; content/metadata v2 wire lengths; and seven 32-byte digests (key commitment, current active-key head, current contribution-grant head, both exact ciphertext wires, predecessor action, enrolled author signing key). All integers are big-endian. Filenames, note text and care dates stay encrypted in metadata and are absent from the signed payload.

The browser signs these bytes with its non-exportable Ed25519 private key. The pending-pair digest is `SHA-256(payload)`. The chained action digest is `SHA-256("adeno:managed:pending-draft-pair-action-hash:v1\0" || payload || signature)`. The existing v10 SQL action kind remains `review` because its trigger requires that value; the signed operation byte and domain distinguish *submitting a pending pair* from any future adult approval.

The pure server verifier checks the exact payload, signature, action digest, counter/predecessor, session/device, paired time and current key/grant evidence against caller-supplied authoritative state. It does **not** establish that the state was actually loaded from SQLite. A future writer must load the reservation, both role-specific intents and committed blobs, wire hashes and lengths, enrolled key, current key/grant heads, account/session/device binding and prior action **inside one `BEGIN IMMEDIATE` transaction**. It must recheck CSRF and active authority, verify the signature, then insert the signed action and pending pair atomically. The device must separately decrypt/authenticate both wires and check the metadata's encrypted `contentBlobId` and plaintext digest before review UI exposure.

Browser and Node tests use wholly fictional IDs, one-byte nonempty v2 wire fixtures, and a fixed synthetic Ed25519 interoperability vector; tampering with identities, either wire, head, session, counter or signature fails. The browser signer's 16 MiB content cap is narrower than the v10 SQL draft-intent allowance; the future writer must adopt one consistent bound. This is a cryptographic contract, not evidence of a mounted write path or an independently auditable persisted record. V10 stores the payload digest and signature but **not the exact canonical payload**. After heads change, an independent auditor cannot reliably reconstruct that preimage. Durable immutable payload retention, anchored to the action and included in authenticated backups, needs a separately reviewed design and any necessary migration approval. The future writer must also explicitly decide whether a pair may be submitted after its reservation's ten-minute window once both blobs committed in time; current SQL does not require an unexpired reservation at pair insertion.
