# Pending draft-pair signed action — unmounted contract

This is a device-authored proposal to place **two already committed ciphertext blobs** into the pending adult-review inbox. It does not approve or publish a care day, interpret medical content, or let the hosted server decrypt anything. No route or writer currently mounts this action; no database migration was created or applied for it.

The shared `encodePendingDraftPairActionPayloadV1` encodes exactly 480 bytes, never JSON: `ADPP` magic; format, Ed25519/SHA-256 suite, a dedicated *register pending pair* operation byte and predecessor flag; 13 ordered opaque 16-byte IDs (household, profile, draft scope, key, reservation, content/metadata intents, content/metadata blobs, content/metadata AAD objects, author device, session); draft key epoch and purpose; author counter and pair time; content/metadata v2 wire lengths; and seven 32-byte digests (key commitment, current active-key head, current contribution-grant head, both exact ciphertext wires, predecessor action, enrolled author signing key). All integers are big-endian. Filenames, note text and care dates stay encrypted in metadata and are absent from the signed payload.

Before signing, the browser opens a draft-purpose HPKE key envelope for the claimed author device and verifies that its scope identity, key ID, epoch and key-material commitment match the signed claims. It then opens both copied v2 wires with that nonextractable envelope-unwrapped key and their claimed AAD object IDs. The authenticated metadata must name the exact content blob and match its plaintext digest, size and file/note format. The signer clears returned file bytes immediately after checking. It then signs the 480 bytes with its non-exportable Ed25519 private key. The pending-pair digest is `SHA-256(payload)`. The chained action digest is `SHA-256("adeno:managed:pending-draft-pair-action-hash:v1\0" || payload || signature)`. The existing v10 SQL action kind remains `review` because its trigger requires that value; the signed operation byte and domain distinguish *submitting a pending pair* from any future adult approval. The signer does not establish that the envelope issuer is authorized or the grant is current; those are separate signed-envelope and transaction checks.

The pure server verifier checks the exact payload, signature, action digest, counter/predecessor, session/device, paired time and current key/grant evidence against caller-supplied authoritative state. It does **not** establish that the state was actually loaded from SQLite or prove either blob was uploaded. A future writer must load the reservation, both role-specific intents and committed blobs, wire hashes and lengths, enrolled key, current key/grant heads, account/session/device binding and prior action **inside one `BEGIN IMMEDIATE` transaction**. It must recheck CSRF and active authority, verify the signature, then insert the signed action and pending pair atomically. The device must separately decrypt/authenticate both wires again before review UI exposure. Upload receipts, including exact wire digest and length, must be confirmed before a client calls this signed submission path; a missing receipt is never proof an intent may be retried.

Browser tests sign genuinely encrypted fictional drafts and reject a wrong key, changed AAD object, tampered content and validly encrypted but unrelated metadata. A separate structural one-byte wire vector tests the shared payload/Ed25519 contract across browser and Node; those structural bytes are **not** an authenticated draft and the browser signer rejects them. The browser signer's 16 MiB content cap is narrower than the v10 SQL draft-intent allowance; the future writer must adopt one consistent bound. This is a cryptographic contract, not evidence of a mounted write path or an independently auditable persisted record. V10 stores the payload digest and signature but **not the exact canonical payload**. After heads change, an independent auditor cannot reliably reconstruct that preimage. Durable immutable payload retention, anchored to the action and included in authenticated backups, needs a separately reviewed design and any necessary migration approval. The future writer must also explicitly decide whether a pair may be submitted after its reservation's ten-minute window once both blobs committed in time; current SQL does not require an unexpired reservation at pair insertion.
